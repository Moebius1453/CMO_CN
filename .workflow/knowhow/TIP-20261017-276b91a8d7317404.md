# 诊断探针与实机用例的三种「自失效」（比产品缺陷更容易被忽略）

## 1) 命令写在不可达的条件块里（死码）
`DUMP_LISTS` 加进引擎时被写进 `if (cmd == "WPF_DUMP" || cmd == "DUMP_COMBOS" || cmd == "XLATE_BATCH")`
块**内部** → 外层条件永远不匹配，调用只会得到 `Unknown command`。
**教训**：给引擎加探针命令后必须**真的调用一次**并看返回——"代码里有"不等于"命令能跑"。
误判代价：上一轮把"没命中"解释成"这个对话框不是 WinForms 列表"，结论是错的。

## 2) 带参数的探针参数不生效（静默退化）
`CTRL_TREE <窗体过滤>` 的调度传的是大写首 token（`HandleCtrlTree(cmd)`），`Substring` 取不到
第二个 token → 过滤词永远为空，带过滤的调用静默返回**全量**控件树。
**教训**：凡"带参数"的探针，要用两个不同参数做**对照实验**验证参数真的生效
（修复后实测：带过滤 23 节点/单窗体 vs 全量 40 节点/2 窗体）。

## 3) 用整窗截图的 md5 判「无频闪」
`R4-live-flicker` 原实现比较窗口截图 md5；而 `GuiDriver capture` 是屏幕抓图
（`CopyFromScreen`），游戏暗色窗口半透明，窗口**背后的动态地图**会被一起抓进来 →
地图一动画两帧必不同，用例假红（实测两帧 UI 文本逐字相同、差异全在背后地图上）。
**教训**：判"文本是否稳定"就直接比**文本状态**（控件文本集合 + 下拉项 + 详情页 HTML 长度/前缀），
截图只作人工复核材料；像素级比对在会动的背景上不可靠。

## 通用原则
- 探针/门禁的可信度要靠**负向用例**与**对照实验**证明（同项目 R23「门禁自身失效」是同一类事故）。
- 一旦发现探针坏了，先修探针再重跑结论——不要拿着坏探针的"0 条 / 没命中"继续推理。
