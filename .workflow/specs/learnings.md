### 发版铁律：缺陷必须登记台账，发版前必须重跑回归 SOP

# 发版铁律：缺陷必须登记台账，发版前必须重跑回归 SOP

## 规则（用户 2026-10-15 明确要求）
1. **每个用户可感知的缺陷都要登记**在 `docs/BUG_REGISTRY.md`（编号 R<n>，只增不改）：
   现象 / 根因 / 改动位置 / 用户可见验收 / 回归测试点。
2. **每个缺陷都必须落一条可执行回归用例**到 `scripts/verify_regressions.py`
   （能自动化就自动化；`--static` 为源码/资产/词库断言，`--live` 为实机用例），
   并在 `docs/CHANGELOG.md` 对应版本段落说明。
3. **每次发版前必须按 `docs/RELEASE_TEST_SOP.md` 执行**：
   环境校验（R0：游戏目录词库与 `dict/` 逐字节一致、引擎含本轮修复标记）→
   `verify_all.py` 10/10 → `verify_regressions.py` 全绿（static+live）→
   `package.sh`（内含 static 回归硬门禁 + 密钥门禁 + 资产覆盖断言）→
   `publish_release.py`（校验 24h 内、同版本、含 live 且全通过的回归报告，否则拒绝上传）→
   发布后自检（latest/HTTP 206/sha256/升级链/实装复测）。

## 为什么（本规则针对的真实事故）
- v4.0.0 已修过一次「数据库查看器详情空白」（改写 ComboBox.Text 破坏游戏分派），
  v4.1.3 的下拉框全量汉化从**通用路径**绕过了当时的专用保护，导致 v4.1.5 复发；
  因为当时**没有台账、没有回归用例**，同一问题隔了两个版本又回到用户面前。
- v4.1.5 发版前还抓到一次真实环境漂移：游戏目录被旧安装包覆盖成不含修复的引擎，
  使回归“失败”实为环境错 → 因此增加 R0 环境校验。
- R0 不能用整文件哈希：csc 每次编译 MVID/时间戳都变，重新 build 后哈希必变；
  应判「词库逐字节一致」+「引擎二进制含关键修复符号」。

## 必须遵守
- 新增缺陷时三件套缺一不可：台账条目 + 回归用例 + CHANGELOG 条目。
- 回归用例是唯一权威：改了引擎/词库/资产却让某条用例失效，必须同步更新用例并说明原因，
  不允许删除用例或降低阈值来「通过」。
- 打包/发布门禁失败必须修复后重跑；仅允许显式 `--force` 绕过并在提交信息/发布说明留痕。
- 手工才能在真实用户路径上验证的项（如消息日志多行教程消息）在台账标注「手动」，
  发版前由人完成并记录证据。

### 补丁类工具安装状态/设置/回退的权威定义（v4.1.6 事故）

# 补丁类工具的「安装状态 / 设置 / 回退」权威定义（v4.1.6 事故后确立）

## 事故（用户原话，2026-10-16）
「为什么我还原了也显示已经安装新版本了，这不就是我想回退也回退不了了么，而且之前的最小化托盘设置
啥的全都没有了。更新频率也没有了。」

## 结论：六条必须遵守的约束
1. **状态真相只能是「部署实证」**：游戏目录内的安装清单（版本 + 时间 + 来源 + 关键文件 sha256）。
   注册表里一个版本字符串只反映「最后运行的那个安装包」，任何旧包一装就把它改成旧版本号 →
   “还原了还显示已安装新版本”，且**任何基于它的回退判断都是错的**。清单缺失时必须自愈
   （有文件无清单 → 按当前文件登记，版本回退链：注册表 → 已部署资产自带版本戳 → unknown），
   否则存量用户/绿色包用户被误报「未安装」。
2. **设置与安装态必须解耦**：设置存用户级配置目录（本项目用 `%APPDATA%`，避免被 `%LOCALAPPDATA%`
   清理逻辑波及），还原/卸载一律保留；清除设置必须是**显式**动作（勾选项或 `--purge-settings`）。
   绝对禁止用「删整个注册表键」的方式做还原——那会静默抹掉用户所有偏好（频率、提醒方式、镜像、自启）。
3. **回退单位应当是整个安装包，不是引擎资产快照**：真实安装足迹远大于 dll+词典
   （本项目实测 Scenarios 323 文件/218MB、Symbols/Menu 158 文件），快照引擎资产会得到
   「旧引擎 + 新资产」的混合安装。做法：安装时把安装包缓存到本机（保留最近 N 个），
   回退 = 用它 `--install` 重装 + 由新版代码补写清单（旧包不会写新清单）+ 校验部署的关键文件
   哈希 == 包内嵌哈希，不一致就拒绝登记（宁可报错也不要混合态被记成"正常"）。
4. **降级提示必须门控**：把「版本不同」当作「有更新」会向运行未发布/内测版本的用户反复推送降级提示。
   只有「远端更旧 **且** 本地确实缓存了该版本包」才提示可回退，否则静默只记日志。
5. **版本号必须单点派生并机械校验**：VERSION 文件 → 安装器常量 → 安装器窗口标题 → 助手常量 →
   词典/资产内嵌版本戳，五处一致由门禁脚本把关。本项目真实事故：词典戳停在 4.1.4 而 VERSION 已到 4.1.5，
   发布包名与包内资产的自我声明不符（还会污染“安装包版本识别”这类按内容读版本的逻辑）。
6. **共享状态逻辑只写一份并配单测宿主**：设置/清单/缓存/回退/门控放进独立源文件，编译进所有相关 EXE；
   另建一个**不进发布包**的测试宿主（本项目 `build/CMOSharedTest.exe`，27 项断言），
   让「原子写、损坏文件回落、注册表迁移、清单往返/篡改检测、缓存保留最近 N、门控真值表」
   能在无游戏、无网络的条件下被门禁强制。

## 测试分层（可复用做法）
- `--static`：源码/资产/单测断言（打包硬门禁；注意打包门禁要能「不覆盖发版报告」，否则发布前
  的 live 报告会被中间门禁冲掉）。
- `--installer`：在系统临时目录里造合成目标目录，用 CLI 跑安装/还原/回退/自愈，
  **不碰真实环境、不需要真实程序运行**。
- `--live`：真机用例，发版前必跑。
任何会改动真实目录/注册表的自动化测试必须自带备份与恢复，否则会把开发机环境弄脏并让后续回归误判。
